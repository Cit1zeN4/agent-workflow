# 02.10. Integration & Compatibility Tests

> Статус: план реализации; код и runtime-проверки не выполнялись.
> Дата подготовки: 2026-10-22. Целевая версия Codex 0.163.0 взята из исходного проекта и требует фактической проверки.

## Цель

Получить воспроизводимые доказательства готовности runtime adapter на целевой Windows-конфигурации.

## Зависимости и границы

**Зависимости:** 02.01–02.09.

Входит: контрактные тесты, реальный smoke, версия/схемы, failure injection и проверка ресурсов. Не входит: полный UI E2E, весь workflow скиллов и packaging этапа 12.

## Основания и статус решений

Основание: приложенные AI-Development-Workflow-Orchestrator.md и 02-codex-runtime-integration.md, а также согласованная декомпозиция этапа 02. ADR ниже фиксируют выбранное проектное направление со статусом «предлагается к реализации». Они не являются результатами испытаний. Актуальная документация по ссылкам проверена 2026-10-22; соответствие полей версии 0.163.0 устанавливается в 02.01 и 02.10.

## Архитектурные решения (ADR)

### ADR-02-11 — Два уровня доказательств

**Статус:** предлагается к реализации. **Дата:** 2026-10-22.

**Контекст:** Fake runtime проверяет гонки воспроизводимо, но не подтверждает совместимость с реальным CLI, аккаунтом и Windows.

**Решение:** Обязательны детерминированные контрактные тесты и отдельный real smoke на Windows. Не запускать платные inference-проверки скрыто и не считать skip успехом.

**Рассмотренные варианты:** Альтернативы: только mocks; только нестабильные AI E2E; проверка номера версии без запуска.

**Последствия:** В обычном CI контрактные тесты автономны; real smoke имеет отдельную явную команду, тестовый каталог и отчёт окружения.

**Пересмотр:** если контракт целевого CLI или real smoke опровергнет предпосылки. Изменение фиксировать новой записью ADR со ссылкой на заменённое решение; не скрывать прежний контекст.

## Последовательность реализации

1. Собрать fake app-server fixtures из таблиц 02.01 и сценариев 02.02–02.09: handshake, chunking, bidirectional IDs, early events, malformed envelopes, timeout, overload, disconnect и гонки interrupt.
2. Подготовить временный Windows-каталог без пользовательских исходников и отдельный тестовый профиль Codex с настроенным доступом. Зафиксировать executable path, версию CLI, Node.js, Windows build, профиль схем и способ установки. Не копировать credentials в отчёт.
3. Real smoke A: старт → handshake → thread/start → turn/start → streaming → completed. Проверять структуру, IDs и итог, не точную формулировку модели.
4. Real smoke B: два последовательных turns с уникальным маркером → restart runtime → thread/resume → проверка контекста. Проверить стабильность storage profile; не объявлять восстановление активного turn.
5. Real smoke C: запустить ограниченный по времени turn с достаточным окном для interrupt; дождаться turn/started, отправить interrupt, наблюдать interrupted. Если turn закончился раньше, пометить сценарий как не проверенный и повторить контролируемо, не выдавать completed за успешный interrupt.
6. Real smoke D: безопасное командное действие и изменение тестового файла только в тестовом каталоге; проверить item events. Pending approval получить предсказуемым сценарием и ответить отказом через адаптер. Проверить структурированный вопрос, если целевая capability доступна; реальная совместимость конкретных скиллов остаётся этапам 05/08.
7. Real smoke E: принудительный выход runtime при активном turn, отсутствие авторизации, неверный launcher, неподдерживаемая версия и крупный event. Проверить OutcomeUnknown, blocked и отсутствие повторного старта.
8. Проверить stop/cleanup: PID и дерево, таймеры/handles, отсутствие активных requests. Сохранить обезличенные transcripts и expected outcomes; лимиты окончательно внести в профиль.
9. Обновить protocol-compatibility.md по наблюдениям и сформировать acceptance-report.md: для каждого обязательного сценария pass/fail/blocked/not-run, доказательство, дата и ограничения.
10. Запуск AI smoke — явное действие исполнителя при реализации, с доступным аккаунтом и возможными расходами. В текущем документировании проверки не выполняются и результаты pass не заявляются.

## Тестовые сценарии

| Сценарий | Ожидаемый результат |
|---|---|
| Fake suite без сети и авторизации | Все обязательные сценарии повторяемы и проходят. |
| Целевая Windows-конфигурация | Все обязательные real smoke имеют фактический pass с evidence. |
| CLI другой версии / отсутствие доступа к модели | Объяснимый fail/blocked, не ложный pass и не silent skip. |
| Завершение turn раньше interrupt | Interrupted не считается проверенным; причина указана. |
| Свежий тестовый каталог по инструкции | Новый исполнитель воспроизводит проверки без ручной правки исходников. |

## Критерии приёмки

- [ ] Контрактные проверки всех обязательных сценариев проходят.
- [ ] На Windows подтверждены thread, turn, stream, interrupt, resume и обратный канал server requests.
- [ ] Профиль версии и fingerprint совпадает с реально испытанным CLI; неизвестная версия отклоняется объяснимо.
- [ ] При сбое нет утечек ожиданий, слепых retries и ложного completed.
- [ ] Отчёт содержит фактические доказательства; обязательный blocked/not-run означает, что этап 02 ещё не принят.

Для закрытия каждого пункта требуется ссылка на тест, transcript или отчёт. Наличие этого файла и проектного ADR не означает выполнение критерия.
