# 02.04. Protocol Initialization

> Статус: план реализации; код и runtime-проверки не выполнялись.
> Дата подготовки: 2026-10-22. Целевая версия Codex 0.163.0 взята из исходного проекта и требует фактической проверки.

## Цель

Разрешать операции адаптера только после подтверждённой инициализации соединения.

## Зависимости и границы

**Зависимости:** 02.01–02.03.

Входит: handshake, readiness, профиль capabilities и диагностика авторизации. Не входит: собственная OAuth-система, UI входа и проверка прав на все модели.

## Основания и статус решений

Основание: приложенные AI-Development-Workflow-Orchestrator.md и 02-codex-runtime-integration.md, а также согласованная декомпозиция этапа 02. ADR ниже фиксируют выбранное проектное направление со статусом «предлагается к реализации». Они не являются результатами испытаний. Актуальная документация по ссылкам проверена 2026-10-22; соответствие полей версии 0.163.0 устанавливается в 02.01 и 02.10.

## Архитектурные решения (ADR)

### ADR-02-05 — Готовность соединения отделена от доступности inference

**Статус:** предлагается к реализации. **Дата:** 2026-10-22.

**Контекст:** Живой процесс и корректный handshake не гарантируют успешный AI-запрос.

**Решение:** Отдельно учитывать processState, connection readiness и authentication/access status. initialize один раз на соединение; затем initialized.

**Рассмотренные варианты:** Альтернативы: считать spawn или initialize достаточным подтверждением всего runtime.

**Последствия:** Внешние модули получают объяснимое состояние; проверка доступа к выбранной модели требует отдельного smoke turn.

**Пересмотр:** если контракт целевого CLI или real smoke опровергнет предпосылки. Изменение фиксировать новой записью ADR со ссылкой на заменённое решение; не скрывать прежний контекст.

## Последовательность реализации

1. Ввести connection states: disconnected, initializing, ready, failed; authentication status: unknown, available, required. Не помещать токены в эти DTO.
2. После running отправить initialize с clientInfo и только проверенными client capabilities. Получить валидный ответ в установленный срок.
3. Отправить initialized через тот же writer; ready установить после успешной локальной записи. У уведомления нет собственного response: не ждать вымышленного ACK.
4. Проверить обязательный профиль 02.01. Не интерпретировать client capabilities как список возможностей сервера; не зондировать поддержку методами с побочными эффектами.
5. Если в целевой схеме есть безопасный метод проверки аккаунта, использовать его с минимальным объёмом данных. Иначе оставить auth unknown и предложить внешнюю настройку CLI; не читать credential files самостоятельно.
6. createThread/resumeThread/startTurn до ready отклонять NotReady без скрытой отправки и очереди. Одновременные start получают общий handshake.
7. При timeout, невалидном ответе или несовместимости снять ready, закрыть соединение и корректно остановить процесс. Повторный handshake требует новой генерации.
8. Зафиксировать отдельно требование real smoke turn для подтверждения inference; успешный model/list не считать доказательством entitlement.

## Тестовые сценарии

| Сценарий | Ожидаемый результат |
|---|---|
| Обычный запуск | initialize response → initialized → ready; порядок подтверждён transcript. |
| createThread до ready | NotReady; в stdin нет thread/start. |
| Ошибка/timeout initialize; повтор initialize | Один отказ и cleanup; нет ложной готовности. |
| Процесс завершён между response и initialized | ready не остаётся true. |
| Handshake успешен, аккаунт не настроен | Протокол готов; inference не объявлен доступным. |

## Критерии приёмки

- [ ] Ни один бизнес-метод не отправляется до handshake.
- [ ] Ровно один initialize на transport generation; новый процесс требует нового handshake.
- [ ] Несовместимость и отсутствие авторизации различимы.
- [ ] Capabilities содержат источник подтверждения; непроверенные свойства не выдаются за поддержку.
