# 02.03. JSON-RPC Transport

> Статус: план реализации; код и runtime-проверки не выполнялись.
> Дата подготовки: 2026-10-22. Целевая версия Codex 0.163.0 взята из исходного проекта и требует фактической проверки.

## Цель

Обеспечить двусторонний JSONL-обмен с корректной корреляцией и ограниченным потреблением ресурсов.

## Зависимости и границы

**Зависимости:** 02.01 и 02.02.

Входит: framing, envelopes, request IDs, таймауты, server requests и backpressure. Не входит: смысл workflow-событий, UI и хранение журнала.

## Архитектурные решения (ADR)

### ADR-02-04 — Узкий транспорт под wire-профиль Codex

**Статус:** предлагается к реализации. **Дата:** 2026-10-22.

**Контекст:** Полный универсальный RPC-клиент может навязать несовместимые проверки и лишние возможности.

**Решение:** Один reader stdout и один сериализованный writer stdin; небольшой транспорт поверх стандартных Node.js streams. Envelope валидируется по профилю 02.01.

**Рассмотренные варианты:** Альтернативы: универсальная JSON-RPC библиотека; отдельный брокер сообщений.

**Последствия:** Нужны собственные тесты framing и корреляции; серверные запросы обрабатываются как полноправная часть протокола.

**Пересмотр:** если контракт целевого CLI или real smoke опровергнет предпосылки. Изменение фиксировать новой записью ADR со ссылкой на заменённое решение; не скрывать прежний контекст.

## Последовательность реализации

1. Закрепить wire-правила из профиля. Современная документация описывает JSON-RPC-подобный обмен без поля jsonrpc; не требовать это поле механически и не добавлять без проверки версии.
2. Разбирать UTF-8 инкрементально: chunk не равен строке, символ может быть разрезан. Поддержать LF и проверенный вариант CRLF; лимит считать по байтам до накопления неограниченной строки.
3. Разделять response result/error, notification и server request. Для клиента генерировать уникальные IDs в пределах runtime generation; входящие IDs сохранять вместе с их исходным типом.
4. Вести независимые карты исходящих ожиданий и входящих server requests: одинаковые IDs в разных направлениях не конфликтуют. Входящий request не завершает клиентский promise.
5. Сериализовать запись целых JSONL-сообщений, учитывать drain и ошибки stdin. Отличать queued/not-sent от dispatched; ошибка после возможной отправки не доказывает отсутствие исполнения.
6. Зафиксировать начальные проектные лимиты: 16 MiB на сообщение, 64 pending client requests, 32 pending server requests, 8 MiB очереди исходящих данных. Сделать настраиваемыми и проверить на реальных fixtures; это не ограничения Codex.
7. Разделить timeout ответа RPC и ожидание завершения turn. При timeout удалить локальное ожидание, сохранить ограниченный tombstone и обработать поздний ответ без повторного старта действия.
8. Повреждённый JSON/envelope, превышение лимита или потеря framing закрывают транспорт с диагностикой; неизвестное корректное notification допускает счётчик. Неизвестный server request получает профильную ошибку либо контролируемую остановку, без автоматического разрешения.
9. При EOF обработать полный остаток только согласно правилам профиля; незавершённую строку считать ошибкой. При disconnect завершить все ожидания и очистить bounded registries.

## Тестовые сценарии

| Сценарий | Ожидаемый результат |
|---|---|
| Две строки в chunk; одна строка в нескольких chunks; разрез UTF-8 | Сообщения восстановлены без повреждений. |
| Responses B, notification, server request, response A | A и B получают свои ответы; server request доставлен отдельно. |
| Одинаковый ID в двух направлениях; ID=0 | Нет смешения; нулевой ID не принят за отсутствие ID. |
| Malformed JSON, длинная строка без LF, EOF посреди JSON | Ограниченный буфер и явный отказ. |
| Timeout, поздний response, дубликат response, write error | Нет двойного settle и повторной отправки; неопределённость обозначена. |

## Критерии приёмки

- [ ] Корреляция выдерживает перемешивание сообщений и оба направления RPC.
- [ ] При превышении лимитов нет тихой потери критичных сообщений и неограниченного роста памяти.
- [ ] Каждое ожидание получает ровно один локальный исход; поздние данные не привязываются к новой генерации.
- [ ] stdin/stdout доступны другим модулям только через Transport.
