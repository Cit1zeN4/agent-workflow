## Архитектурные решения (ADR)

### ADR-02-09 — Прерывание требует наблюдаемого подтверждения

**Статус:** предлагается к реализации. **Дата:** 2026-10-22.

**Контекст:** Пользовательское намерение остановить работу не доказывает, что runtime уже прекратил действия.

**Решение:** interruptTurn отправляет проверенный RPC и ожидает отдельного terminal event; cancel local wait не посылает interrupt; stop runtime прекращает весь процесс.

**Рассмотренные варианты:** Альтернативы: приравнять timeout к отмене; убивать процесс при каждом cancel; считать interrupt ACK конечным interrupted.

**Последствия:** Есть отдельные лимиты ожидания RPC и подтверждения остановки. При отсутствии доказательства сохраняется OutcomeUnknown; изменения не откатываются автоматически.

**Пересмотр:** если контракт целевого CLI или real smoke опровергнет предпосылки. Изменение фиксировать новой записью ADR со ссылкой на заменённое решение; не скрывать прежний контекст.

## Последовательность реализации

1. Описать три операции в публичном контракте: interruptTurn(thread/turn handle), stop и локальное прекращение ожидания. Для каждой указать воздействие на runtime и возвращаемое подтверждение.
2. Проверить принадлежность turn текущей generation и active execution. Повторный interrupt объединять в одно наблюдаемое намерение, не отправлять бесконечные RPC.
3. После interrupt ACK оставить interruptRequested до terminal. Если раньше приходит completed или failed, вернуть именно фактический статус, а запрос interrupt отметить отдельно.
4. Если terminal interrupted приходит до ACK, завершить наблюдение исполнения; поздний ACK/error хранить как диагностику без замены уже подтверждённого статуса.
5. Выбрать начальные проектные лимиты: RPC 15 s, terminal-after-interrupt 15 s, stop grace 5 s, force-close 5 s; они настраиваются и валидируются на Windows. Таймаут означает истечение ожидания, не откат.
6. По истечении подтверждения вернуть OutcomeUnknown и blocked. Остановку процесса выполнять по явному вызову stop или согласованной политике владельца, а не выдавать убийство процесса за успешный interrupt.
7. При local cancel отсоединить конкретного ожидающего потребителя, но сохранить adapter observation и active slot. При stop завершить всё по правилам 02.02/02.09.
8. Проверить pending server requests: отказать в устаревших ответах; если runtime поддерживает событие разрешения запроса — нормализовать его. Потеря процесса делает request handles недействительными.

## Тестовые сценарии

| Сценарий | Ожидаемый результат |
|---|---|
| Активный turn → interrupt ACK → interrupted | Подтверждён interrupted, не просто request accepted. |
| Turn успел completed перед interrupt | Сохранён completed; нет ложного interrupted. |
| Terminal раньше ACK; дубли interrupt | Один локальный итог; ограниченное число запросов. |
| Нет ACK/terminal или процесс умер | OutcomeUnknown и невозможность слепого повтора. |
| Отменён локальный waiter | Turn продолжает наблюдаться; слот занят. |
| Прерывание при pending approval | Поздний ответ не применяется к завершённому/новому turn. |

## Критерии приёмки

- [ ] Три вида отмены имеют различимые эффекты и результаты.
- [ ] Каждый interrupt завершается подтверждённым terminal outcome либо OutcomeUnknown в конечное время.
- [ ] Гонки с normal completion и disconnect не меняют доказанный итог.
- [ ] Остановка процесса не обещает откат файлов или отсутствие уже выполненных действий.

Для закрытия каждого пункта требуется ссылка на тест, transcript или отчёт. Наличие этого файла и проектного ADR не означает выполнение критерия.
