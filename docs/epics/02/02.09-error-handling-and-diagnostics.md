# 02.09. Error Handling & Diagnostics

> Статус: план реализации; код и runtime-проверки не выполнялись.
> Дата подготовки: 2026-10-22. Целевая версия Codex 0.163.0 взята из исходного проекта и требует фактической проверки.

## Цель

Дать вызывающим модулям объяснимые ошибки и степень определённости результата без утечки содержимого задач и секретов.

## Зависимости и границы

**Зависимости:** 02.02–02.08; базовые error DTO согласовать уже в 02.05.

Входит: типы ошибок, sanitization, diagnostics и отсутствие слепых retries. Не входит: UI ошибок, централизованный telemetry backend и процедуры восстановления этапа 11.

## Основания и статус решений

Основание: приложенные AI-Development-Workflow-Orchestrator.md и 02-codex-runtime-integration.md, а также согласованная декомпозиция этапа 02. ADR ниже фиксируют выбранное проектное направление со статусом «предлагается к реализации». Они не являются результатами испытаний. Актуальная документация по ссылкам проверена 2026-10-22; соответствие полей версии 0.163.0 устанавливается в 02.01 и 02.10.

## Архитектурные решения (ADR)

### ADR-02-10 — Ошибка отдельно от определённости результата

**Статус:** предлагается к реализации. **Дата:** 2026-10-22.

**Контекст:** Одинаковый timeout может означать неотправленный запрос либо уже выполняемое действие.

**Решение:** Описывать category, phase, dispatchState, outcomeCertainty, generation и доступные IDs. Автоповтор изменяющих операций при неизвестном исходе запрещён. Диагностика по allowlist.

**Рассмотренные варианты:** Альтернативы: единый текст Error; retry любого timeout; логирование всех raw envelopes.

**Последствия:** Логи компактнее и безопаснее; расследование иногда потребует специального обезличенного fixture вместо полного production transcript.

**Пересмотр:** если контракт целевого CLI или real smoke опровергнет предпосылки. Изменение фиксировать новой записью ADR со ссылкой на заменённое решение; не скрывать прежний контекст.

## Последовательность реализации

1. Ввести категории ProcessError, ProtocolError, InitializationError, CompatibilityError, AuthenticationRequired, AccessDenied, RequestTimeout, RuntimeDisconnected, ExecutionFailed и OutcomeUnknown. Добавить NotReady, Busy, UnsupportedCapability, StaleRequest/Conflict для ошибок публичного API.
2. OutcomeUnknown определить как локальный результат наблюдения, а не новый статус Codex. RequestTimeout может сопровождаться outcomeCertainty=unknown; не заменять всю цепочку причин одной категорией.
3. Зафиксировать поля: stableCode, safeMessage, phase, dispatchState (notSent/dispatched/unknown), outcomeCertainty (known/unknown), generation, correlation/thread/turn IDs и safe protocol code. Raw cause не сериализовать автоматически.
4. Составить mapping: spawn failure до отправки → known not-started; RPC validation rejection → известный отказ запроса; disconnect после отправки → unknown, пока нет terminal proof; turn failed → подтверждённый failure.
5. Запретить retries createThread/startTurn/ответов approvals после dispatch с неизвестным исходом. Даже read-only retries не добавлять глобально в MVP; восстановление владельца описать отдельно.
6. В штатном логе хранить method, IDs, duration, byte counts, version/fingerprint, state transition и stableCode. По умолчанию исключить prompts, полные ответы, env, tokens, команды, содержимое файлов и raw stderr.
7. stderr дренировать постоянно, но фильтровать/редактировать до сохранения; bounded ring buffer 64 KiB очищенного текста — начальное проектное ограничение. Управляющие символы нормализовать, ошибки redaction не должны выпускать raw данные.
8. Считать pending requests, queue bytes, last event time и exit code. Диагностика не объявляет readiness или turn success по одному отсутствию ошибок.
9. Проверить двойные причины close/exit/error, поздний response и terminal event: единственный локальный settle, позднее подтверждение — отдельное событие сверки для этапа 11.

## Тестовые сценарии

| Сценарий | Ожидаемый результат |
|---|---|
| Сбой до отправки и после отправки | Разная dispatchState и определённость; retry не происходит автоматически. |
| Prompt/token/private path/ANSI в stderr и error.data | В штатном логе нет исходного содержимого и управляющих последовательностей. |
| exit, close и error для одного сбоя | Один локальный исход, причины не порождают дублированные execution results. |
| Поток неизвестных событий / длинный stderr | Буферы и число диагностик ограничены. |
| Понятное человеку описание несовместимости | Есть фактическая версия, требуемый профиль и действие для исправления без секретов. |

## Критерии приёмки

- [ ] Каждая ошибка публичного API имеет stableCode, последствия и определённость.
- [ ] Timeout не трактуется как доказательство отсутствия действия.
- [ ] Секреты и содержимое задач отсутствуют в обычной диагностике; буферы ограничены.
- [ ] После disconnect нет pending promises без конечного локального исхода; автоповтор изменяющих операций не выполняется.

Для закрытия каждого пункта требуется ссылка на тест, transcript или отчёт. Наличие этого файла и проектного ADR не означает выполнение критерия.
