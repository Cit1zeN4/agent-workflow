# 02.01. Protocol Research & Compatibility

> Статус: план реализации; код и runtime-проверки не выполнялись.
> Дата подготовки: 2026-10-22. Целевая версия Codex 0.163.0 взята из исходного проекта и требует фактической проверки.

## Цель

Получить воспроизводимый контракт целевого Codex и определить, какие возможности адаптер вправе использовать.

## Зависимости и границы

**Зависимости:** Этап 01 Project Foundation.

Входит: версия и способ установки CLI, экспорт контрактов, реестр методов, совместимость и список пробелов. Не входит: реализация транспорта, запуск AI-задач, полноценный HITL и поддержка нескольких версий.

## Основания и статус решений

Основание: [docs/project.md](../../project.md) и [02-codex-runtime-integration.md](02-codex-runtime-integration.md), а также согласованная декомпозиция этапа 02. ADR ниже фиксируют выбранное проектное направление со статусом «предлагается к реализации». Они не являются результатами испытаний. Актуальная документация по ссылкам проверена 2026-10-22; соответствие полей версии 0.163.0 устанавливается в 02.01 и 02.10.

## Архитектурные решения (ADR)

### ADR-02-01 — Codex App Server через stdio

**Статус:** предлагается к реализации. **Дата:** 2026-10-22.

**Контекст:** Проекту нужны длительные сессии, поток событий и двустороннее взаимодействие.

**Решение:** Сохранить App Server со stdio как единственный runtime MVP. Не добавлять SDK или WebSocket.

**Рассмотренные варианты:** Альтернативы: codex exec для отдельных задач; SDK для более высокого уровня интеграции.

**Последствия:** Адаптер владеет протоколом и процессом; смена runtime потребует новой реализации адаптера, а не изменений Workflow Engine.

**Пересмотр:** если контракт целевого CLI или real smoke опровергнет предпосылки. Изменение фиксировать новой записью ADR со ссылкой на заменённое решение; не скрывать прежний контекст.

### ADR-02-02 — Контракты из целевой установки

**Статус:** предлагается к реализации. **Дата:** 2026-10-22.

**Контекст:** Актуальная веб-документация может отличаться от версии, указанной в проекте.

**Решение:** Экспортировать TS и JSON Schema целевым CLI, хранить результат с версией, хешами и инструкцией воспроизведения. Проверять критичные входные данные во время выполнения.

**Рассмотренные варианты:** Альтернативы: ручное описание полного протокола или зависимость от контрактов latest.

**Последствия:** Обновление CLI — отдельное изменение контрактов и повтор smoke test; TS-типы сами по себе не валидируют входящие JSON.

**Пересмотр:** если контракт целевого CLI или real smoke опровергнет предпосылки. Изменение фиксировать новой записью ADR со ссылкой на заменённое решение; не скрывать прежний контекст.

## Последовательность реализации

1. Сверить исходную конфигурацию проекта с фактической Windows-установкой. Версии 0.163.0 / Node.js 24.21.0 / Git 2.55.0 пока считать заявленными, а не проверенными здесь.
2. На целевой машине сохранить вывод версии и справки app-server; проверить наличие generate-ts и generate-json-schema. Синтаксис экспорта уточнить по справке этой установки.
3. Выгрузить контракты в отдельный каталог без ручных правок; записать команду, версию, платформу, дату и SHA-256 файлов.
4. Составить таблицу: направление, wire method, параметры, результат, ошибки, экспериментальный флаг, обязательность, источник и фактическое доказательство. Включить initialize/initialized, thread/start, thread/resume, turn/start, turn/interrupt, turn/completed и используемые item-события.
5. Отдельно исследовать server requests для approvals и пользовательского ввода: точные имена, допустимые ответы, разрешение/истечение запроса. Список из современной документации не переносить автоматически в 0.163.0.
6. Для MVP объявить обязательными start/resume thread, turn, interrupt, terminal events и маршрутизацию интерактивных запросов. Неподтверждённая поддержка блокирует приёмку требующей её функции; ограниченный smoke допустим только с явно указанным пропуском.
7. Определить профиль разрешённой версии и fingerprint схем. Не предполагать наличие универсального RPC для перечисления всех возможностей: capabilities выводятся из профиля и целевых проверок.
8. Заполнить protocol-compatibility.md и перечень оставшихся проверок для 02.10.

## Тестовые сценарии

| Сценарий | Ожидаемый результат |
|---|---|
| Повторный экспорт тем же CLI | Совпадает содержимое контрактов либо объяснены только недетерминированные метаданные. |
| Отсутствует обязательный метод | Профиль несовместим; возможность не объявлена поддерживаемой. |
| CLI другой версии / неизвестный fingerprint | Получена понятная несовместимость; обновление не принято молча. |
| Метод виден в документации, но отсутствует в схеме | Он отмечен как неподтверждённый и не используется. |

## Критерии приёмки

- [ ] Реестр покрывает каждую операцию и событие, нужные 02.02–02.10; для каждого есть направление, обязательность и источник.
- [ ] Есть воспроизводимый экспорт, версия CLI и хеши без секретов.
- [ ] Поддержка resume и интерактивных ответов явно подтверждена либо указана как блокирующая проверка.
- [ ] Сведения из документации отделены от результатов фактических запусков.

Для закрытия каждого пункта требуется ссылка на тест, transcript или отчёт. Наличие этого файла и проектного ADR не означает выполнение критерия.
