> Статус: план реализации; код и runtime-проверки не выполнялись.

## Цель

Закрепить стабильный интерфейс runtime для Session Manager, Workflow Engine и HITL Manager.

## Зависимости и границы

**Зависимости:** 02.01; согласование с 02.02–02.04. Черновик контракта создаётся до реализации транспорта, финализация — здесь.

## Архитектурные решения (ADR)

### ADR-02-06 — Доменный адаптер с обратным каналом

**Статус:** предлагается к реализации. **Дата:** 2026-10-22.

**Контекст:** Прямые импорты Codex DTO связывают бизнес-логику с версией протокола; одних notification недостаточно для HITL.

**Решение:** Публичные DTO независимы от Codex. Добавить response operation для runtime requests и единый типизированный поток событий с явной отпиской.

**Рассмотренные варианты:** Альтернативы: экспорт generated types в Workflow Engine; EventEmitter с произвольными payload; только односторонний stream.

**Последствия:** Mapping и schema validation остаются внутри адаптера. Для нового runtime потребуется поддержать тот же небольшой набор семантик.

**Пересмотр:** если контракт целевого CLI или real smoke опровергнет предпосылки. Изменение фиксировать новой записью ADR со ссылкой на заменённое решение; не скрывать прежний контекст.

## Последовательность реализации

1. Разделить workflowRunId, sessionId, executionId (владельцы — внешние модули) и opaque runtimeThreadId/runtimeTurnId/requestHandle (владелец — адаптер). Не отождествлять их.
2. Описать start, stop, getCapabilities, createThread, resumeThread, startTurn, interruptTurn, subscribe и respondToRuntimeRequest. Последнее принимает внутренний requestHandle и типизированное решение, не raw JSON-RPC.
3. Для startTurn возвращать execution handle: локальный correlationId, подтверждённый runtimeTurnId при наличии, отдельное ожидание локального итогового результата. RPC ACK и завершение execution различать.
4. Event envelope: schemaVersion, runtimeGeneration, sequence, observedAt, kind, доступные threadId/turnId/correlationId и нормализованный payload. sequence задаёт порядок наблюдения внутри генерации, не глобальный порядок времени.
5. Определить события ready/disconnected, thread created/resumed, turn started/finished, message delta, item lifecycle, runtime request opened/resolved, diagnostics. Итог turn включает completed/failed/interrupted либо локальный outcomeUnknown без подмены runtime status.
6. Определить bounded ordered dispatcher: подписчик не блокирует reader; отказ потребителя или переполнение видны явно. Критичные events не теряются тихо. Подписка получает только будущие события, replay будет в этапе 03.
7. requestHandle связать с generation и исходным server ID. Повторный или устаревший ответ отклонять; после disconnect ответы недействительны. Политика вопроса и персистентная дедупликация принадлежат этапу 05.
8. Сопоставить capabilities с операциями; отсутствие поддержки даёт UnsupportedCapability до отправки. Проверить импортные границы модулей.

## Тестовые сценарии

| Сценарий | Ожидаемый результат |
|---|---|
| Fake adapter вместо Codex | Session/Workflow consumer работает без импортов generated DTO. |
| Запрос разрешения → ответ через adapter | Ровно один исходящий ответ с исходным wire ID. |
| Ответ после restart / повтор ответа | StaleRequest или Conflict; новая операция не затронута. |
| Отписка / медленный или ошибочный consumer | Ресурсы освобождены; отказ доставки виден, reader не блокируется. |
| Unknown runtime event | Не ломает стабильный публичный контракт; диагностика ограничена. |

## Критерии приёмки

- [ ] Контракт покрывает lifecycle, thread/turn, streaming, interrupt и обратный канал HITL.
- [ ] Внешние модули не импортируют protocol types и не видят сырые permissions envelopes.
- [ ] Семантика ACK, local result, runtime terminal status и OutcomeUnknown различается.
- [ ] Порядок, лимиты, отписка, повторы ответов и disconnect задокументированы и проверены.

Для закрытия каждого пункта требуется ссылка на тест, transcript или отчёт. Наличие этого файла и проектного ADR не означает выполнение критерия.
