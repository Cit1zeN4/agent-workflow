# 02.07. Turn Execution & Streaming

> Статус: план реализации; код и runtime-проверки не выполнялись.

## Цель

## Архитектурные решения (ADR)

### ADR-02-08 — ACK не завершает execution

**Статус:** предлагается к реализации. **Дата:** 2026-10-22.

**Контекст:** Подтверждение turn/start означает принятие запроса; потеря связи не доказывает неуспех действия.

**Решение:** Итог определять по валидному terminal event. Ввести локальный OutcomeUnknown при потере подтверждения и не повторять startTurn автоматически. В MVP один активный turn на весь адаптер.

**Рассмотренные варианты:** Альтернативы: считать ACK успехом; считать любой turn/completed успехом; запускать дубли при timeout.

**Последствия:** Глобальная последовательность MVP проще; несколько threads остаются доступными для последовательной работы. Успех runtime не завершает бизнес-этап автоматически.

**Пересмотр:** если контракт целевого CLI или real smoke опровергнет предпосылки. Изменение фиксировать новой записью ADR со ссылкой на заменённое решение; не скрывать прежний контекст.

## Последовательность реализации

1. До отправки зарегистрировать локальный correlationId и наблюдение событий; захватить один слот активного execution. Повторный start до освобождения слота получает Busy.
2. Сформировать turn/start из проверенных входных DTO; проверить ACK и связать runtimeTurnId. Уведомления могут прийти до обработки ACK: использовать небольшой bounded early-event buffer по generation/thread/turn и разрешить mapping после ответа.
3. Статусы локального наблюдения: starting, running, interruptRequested, completed, failed, interrupted, outcomeUnknown. Последние четыре — конечные локальные исходы; outcomeUnknown не является wire-status Codex.
4. Нормализовать agent message delta, item started/completed, команды и file changes, runtime requests. Не трактовать текст stdout инструмента как отдельное RPC-сообщение.
5. Назначать sequence в момент чтения нормализуемого события до асинхронной доставки. Не обещать порядок между stderr и stdout или между разными поколениями процесса.
6. Для turn/completed проверить ID, schema и status. completed/failed/interrupted переводить в соответствующий результат; незнакомый terminal status не считать успехом. RPC error до принятия отделять от execution failure.
7. Не конкатенировать final item повторно с уже доставленными deltas: хранить итоговый snapshot отдельно. Если подписчик присоединился поздно, полного replay без этапа 03 нет.
8. Ограничить event queue: стартовый бюджет 8 MiB и 4096 событий, далее уточнить по fixtures. При переполнении прекратить новые starts, инициировать управляемую остановку и явно указать потерю наблюдаемости. Даже после остановки не считать изменения отменёнными.
9. При недоступном ACK/terminal event завершить локальное ожидание OutcomeUnknown, слот перевести в blocked. Разблокирование только после подтверждённого завершения или явной остановки и сверки; локальный timeout не разрешает второй turn. Позднее доказательство отдать отдельным reconciliation event без второго settle.

## Тестовые сценарии

| Сценарий | Ожидаемый результат |
|---|---|
| Обычный turn с текстом и item events | Поток доступен до завершения; итог completed один. |
| turn/completed со failed или interrupted | Нет успешного результата. |
| Terminal event раньше ACK, повтор terminal, неизвестный turn ID | Сопоставление корректно; нет второго результата или привязки к чужому turn. |
| Обрыв после принятия start / пропавший terminal event | OutcomeUnknown и blocked, повтор старта не выполняется. |
| Медленный consumer / переполнение очереди / повтор final snapshot | Нет тихой потери terminal event и дублирования финального текста. |

## Критерии приёмки

- [ ] Внешний модуль получает структурированный stream и один локальный итог без разбора протокола.
- [ ] Успех определяется terminal status, а не именем уведомления или ACK.
- [ ] Наблюдаемый порядок, корреляция ранних событий и лимиты подтверждены fixtures.
- [ ] OutcomeUnknown не освобождает возможность слепого повторного запуска; бизнес-проверка результата остаётся этапу 08.

Для закрытия каждого пункта требуется ссылка на тест, transcript или отчёт. Наличие этого файла и проектного ADR не означает выполнение критерия.
