# 02.02. Runtime Process Lifecycle

> Статус: план реализации; код и runtime-проверки не выполнялись.
> Дата подготовки: 2026-10-22. Целевая версия Codex 0.163.0 взята из исходного проекта и требует фактической проверки.

## Цель

Сделать запуск, наблюдение и остановку локального Codex управляемыми и ограниченными по времени.

## Зависимости и границы

**Зависимости:** 02.01; готовый backend этапа 01.

Входит: разрешение исполняемого файла, окружение, stdio и события процесса. Не входит: handshake, бизнес-восстановление, менеджер процессов на каждый turn.

## Основания и статус решений

Основание: приложенные AI-Development-Workflow-Orchestrator.md и 02-codex-runtime-integration.md, а также согласованная декомпозиция этапа 02. ADR ниже фиксируют выбранное проектное направление со статусом «предлагается к реализации». Они не являются результатами испытаний. Актуальная документация по ссылкам проверена 2026-10-22; соответствие полей версии 0.163.0 устанавливается в 02.01 и 02.10.

## Архитектурные решения (ADR)

### ADR-02-03 — Один процесс с явным владельцем

**Статус:** предлагается к реализации. **Дата:** 2026-10-22.

**Контекст:** MVP выполняет workflow последовательно и должен освобождать ресурсы предсказуемо.

**Решение:** Один управляемый App Server на backend; запуск средствами Node.js child_process с массивом аргументов, shell:false. Process Manager владеет процессом, Transport — обменом stdio.

**Рассмотренные варианты:** Альтернативы: процесс на turn, внешняя служба, пул процессов.

**Последствия:** Несколько threads допустимы, но параллельные AI-executions не входят в MVP. Сбой процесса затрагивает все его незавершённые операции.

**Пересмотр:** если контракт целевого CLI или real smoke опровергнет предпосылки. Изменение фиксировать новой записью ADR со ссылкой на заменённое решение; не скрывать прежний контекст.

## Последовательность реализации

1. Определить конфигурацию absolute executable path, args, cwd, allowlist необходимых env и лимиты остановки. Не переносить токены в диагностические сообщения.
2. Проверить Windows-способ установки. Если PATH разрешает только codex.cmd, нельзя просто включить shell:true: найти исполняемый бинарник либо проверенный JS entrypoint пакета и запускать его через абсолютный node.exe. Зафиксировать выбранный launcher в профиле.
3. Описать переходы stopped → starting → running → stopping → stopped; failed при ошибке. running означает живой процесс, ready появится только после 02.04.
4. Защитить start/stop от гонок: повторный start разделяет один результат, повторный stop безопасен, start во время stopping получает Busy. Состояния и слушатели принадлежат одной генерации процесса.
5. Развести stdout протокола и stderr диагностики. Подключить обработку spawn error, EOF, exit и close без двойного завершения операций.
6. Остановка: запретить новые запросы, начать согласованное завершение ввода/процесса согласно проверенному поведению, ждать ограниченное время, затем принудительно завершать. Не предполагать существование RPC shutdown.
7. Для Windows проверить завершение дерева дочерних процессов и ограниченный fallback. До подтверждения отсутствия оставшихся процессов не считать остановку чистой.
8. После exit передать транспорту причину, завершить ожидания, освободить таймеры и подписки. Для отправленных действий сохранить возможность OutcomeUnknown.

## Тестовые сценарии

| Сценарий | Ожидаемый результат |
|---|---|
| Десять одновременных start | Ровно один процесс и один итог запуска. |
| Путь с пробелами и кириллицей; аргументы с метасимволами | Аргументы не интерпретируются shell; cwd соответствует конфигурации. |
| Нет бинарника / нет доступа / процесс сразу вышел | Типизированная ошибка без зависших ожиданий. |
| Процесс не выходит при штатной остановке | Срабатывает лимит и fallback; состояние дерева процессов отражено явно. |
| stop во время starting; повтор stop | Один согласованный результат, нет утечек и нового процесса. |

## Критерии приёмки

- [ ] В целевой Windows-конфигурации работают запуск, остановка и повторный запуск.
- [ ] running не выдаётся за готовность API.
- [ ] Каждое ожидание при сбое завершается ровно один раз с корректной определённостью результата.
- [ ] После остановки нет необъяснённых открытых handles и оставшихся процессов; ограничения перечислены.

Для закрытия каждого пункта требуется ссылка на тест, transcript или отчёт. Наличие этого файла и проектного ADR не означает выполнение критерия.
