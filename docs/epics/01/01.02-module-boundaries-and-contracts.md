# 01.02. Границы модулей и общие контракты

> Статус: план реализации; контракты подлежат уточнению на следующих этапах.

## Цель

Дать модулям общий словарь типов и направленные зависимости без смешения workflow, сессии и отдельного выполнения.

## Зависимости и границы

**Зависимости:** 01.01. Входит: роли Workflow Engine, Session Manager, HITL Manager, Agent Runtime Adapter, Project Manager и Persistence Layer; базовые идентификаторы и DTO. Не входит: внутренний протокол Codex, политика workflow, таблицы SQLite и реализации модулей.

## Последовательность реализации

1. Описать владельца каждого объекта: project, workflow run, stage, agent session, agent execution, event и user request. Различить внутренние ID и opaque идентификаторы runtime.
2. Нарисовать направленные зависимости между модулями; для вызываемых возможностей задать узкие интерфейсы и владельца результата.
3. Зафиксировать базовые состояния и ошибки только там, где их смысл уже определён; детали runtime уточнит 02.05, персистентности — 03, сессий — 04.
4. Добавить проверку импортных границ или эквивалентный архитектурный тест, чтобы не появились циклы и протокольные DTO вне адаптера.

## Тестовые сценарии

| Сценарий | Ожидаемый результат |
|---|---|
| Один run, два sessions, несколько executions | Идентификаторы и связи не смешиваются. |
| Fake runtime вместо Codex | Потребители используют общий контракт без импорта wire DTO. |
| Запрещённая циклическая зависимость | Проверка сообщает о нарушении. |

## Критерии приёмки

- [ ] У каждого базового типа и действия указан владелец.
- [ ] Run, session и execution представлены разными типами и идентификаторами.
- [ ] Модули не образуют циклов; детали App Server скрыты за адаптером.

## Ожидаемые артефакты

Таблица границ, пакет общих типов и проверка зависимостей.

## Открытые вопросы и проверки

Точные формы событий и состояний требуют согласования с 02.05 и 03.02; расширять типы после фактической проверки соответствующего контракта.
