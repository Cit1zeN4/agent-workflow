# 11.02. Продолжение сессии и ручное восстановление

> Статус: план реализации; проверки не выполнялись.

## Цель

Вернуть доступный контекст Codex после сбоя и предложить управляемое решение, когда продолжение не подтверждено.

## Зависимости и границы

**Зависимости:** 02.06, 04, 11.01. Входит: проверка возможности `thread/resume`, выбор безопасного пути и контекст для нового execution. Не входит: автоматический перезапуск неизвестного действия и политика создания session этапа 04.

## Последовательность реализации

1. После сверки проверить сохранённые runtime identifiers и совместимость текущего профиля CLI.
2. Вызвать поддерживаемый механизм resume и сохранить результат; различать восстановление thread и состояние прежнего turn.
3. Если resume невозможен, показать причину и сформировать пакет контекста из сохранённых артефактов и подтверждённых результатов, без предположений о незаписанной работе.
4. Предоставить допустимые ручные решения: оставить заблокированным, подтвердить завершение по внешнему доказательству или создать новую попытку с явным предупреждением о неизвестном исходе.
5. Каждое решение записывать с пользователем, основанием и связью с исходным execution; прежнюю историю не переписывать.

## Тестовые сценарии

| Сценарий | Ожидаемый результат |
|---|---|
| Thread продолжен | Контекст доступен; старый turn не объявлен автоматически продолженным. |
| Thread недоступен | Предложен пакет подтверждённого контекста и ручной выбор. |
| Неизвестен исход записи файлов | Новый turn не запускается без решения пользователя. |

## Критерии приёмки

- [ ] Успешный resume подтверждается runtime и отражается в session history.
- [ ] Невозможность resume не скрывается созданием новой session.
- [ ] Ручное решение прослеживается до исходного execution и его доказательств.

## Ожидаемые артефакты

Сервис восстановления session, контекстный пакет и сценарии resume/fallback.

## Открытые вопросы

Какие runtime identifiers сохраняют смысл после смены профиля или версии CLI? Решение зависит от проверки 02.10.
