# 11.04. Защита от повторных действий

> Статус: план реализации; проверки не выполнялись.

## Цель

Не допустить двойной отправки ответа, запуска этапа или повтора действия с неизвестным результатом.

## Зависимости и границы

**Зависимости:** 03, 05, 06, 09, 11.01–11.03. Входит: устойчивые ключи операции, ограничения переходов и ручное разрешение неизвестного исхода. Не входит: слепой retry runtime и автоматический push/merge.

## Последовательность реализации

1. Перечислить операции с побочным эффектом: старт execution, ответ HITL, изменение workspace, Git commit и последующие Git-действия.
2. Задать для каждой операции устойчивый ключ и сохранять намерение до отправки; завершение фиксировать отдельно от подтверждения приёма.
3. При повторном вызове возвращать сохранённый результат либо конфликт, не запускать побочный эффект ещё раз.
4. Для `OutcomeUnknown` блокировать автоматический повтор и предоставить процедуру проверки файлов, Git и журнала перед решением пользователя.
5. Проверить гонки между двумя вкладками, перезапуск backend между записью намерения и ответом runtime, поздние события.

## Тестовые сценарии

| Сценарий | Ожидаемый результат |
|---|---|
| Два одинаковых ответа HITL | Один ответ принят, второй получает тот же итог или конфликт. |
| Два старта этапа одновременно | Создано одно execution. |
| Сбой после Git-команды до фиксации итога | Исход неизвестен; команда не повторяется автоматически. |

## Критерии приёмки

- [ ] Для перечисленных побочных эффектов определены ключ и правила повтора.
- [ ] Дубли после рестарта не создают второе действие.
- [ ] Неизвестный исход требует доказательства или явного ручного решения.

## Ожидаемые артефакты

Реестр операций, ограничения БД/API и тесты гонок.

## Открытые вопросы

Какие операции можно безопасно сверить по устойчивому внешнему идентификатору, а какие требуют ручной проверки?
