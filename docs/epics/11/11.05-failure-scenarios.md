# 11.05. Проверки надёжности

> Статус: план реализации; проверки не выполнялись.

## Цель

Подтвердить поведение восстановления при управляемых сбоях до полного E2E этапа 12.

## Зависимости и границы

**Зависимости:** 11.01–11.04. Входит: fault injection и проверка инвариантов восстановления. Не входит: полная поставка Windows-приложения и сквозной сценарий всех скиллов этапа 12.

## Последовательность реализации

1. Создать контролируемые точки сбоя до и после записи намерения, runtime ACK, terminal event, ответа HITL и Git-операции.
2. Сохранять исходное состояние, выполнять сбой, перезапускать backend и сверять БД, runtime, workspace и UI.
3. Проверить повторные запросы API, переподключение SSE и конкурентные вкладки.
4. Для каждого сценария фиксировать ожидаемый статус: восстановлен, прерван, требует вмешательства, либо тест заблокирован из-за отсутствия реальной capability.
5. Составить отчёт с доказательствами и не считать `blocked`/`not-run` успешной проверкой.

## Тестовые сценарии

| Сценарий | Ожидаемый результат |
|---|---|
| Backend завершён во время turn | Нет ложного успеха или автоматического повтора. |
| Runtime исчез при pending approval | Устаревший ответ отклонён, UI показывает причину. |
| Backend завершён после Git-действия | Повтор не выполняется; возможна сверка следа в Git. |

## Критерии приёмки

- [ ] Набор сценариев покрывает ключевые окна между намерением и подтверждением.
- [ ] После каждого сбоя состояние и допустимое действие объяснимы пользователю.
- [ ] Ни один сценарий с неизвестным исходом не приводит к тихому повтору.

## Ожидаемые артефакты

Fault-injection fixtures, автоматические тесты и отчёт о восстановлении.

## Открытые вопросы

Какие реальные сбои Codex воспроизводимы на целевой Windows-конфигурации, определяется после 02.10.
