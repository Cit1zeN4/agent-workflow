# 11.03. Восстановление HITL и интерфейса

> Статус: план реализации; проверки не выполнялись.

## Цель

Показать пользователю актуальные запросы и состояние run после переподключения, не отвечая в мёртвый runtime-запрос.

## Зависимости и границы

**Зависимости:** 03, 05, 10, 11.01. Входит: повторная загрузка состояния и событий, проверка живости pending HITL request, разрешённые действия в UI. Не входит: новые формы HITL и базовый SSE-контракт.

## Последовательность реализации

1. При открытии UI получать сохранённый снимок и продолжать события с указанной позиции; корректно обрабатывать разрыв между ними.
2. Для каждого ожидающего вопроса сопоставить сохранённый request handle с текущей runtime generation и результатом сверки execution.
3. Различать живой запрос, запрос с уже данным ответом, устаревший запрос и запрос с неизвестным исходом ответа.
4. Для устаревшего запроса убрать возможность отправить ответ в runtime и показать причину и доступное ручное восстановление.
5. Проверить конкурентные обновления страницы и повторное подключение нескольких вкладок одного локального пользователя.

## Тестовые сценарии

| Сценарий | Ожидаемый результат |
|---|---|
| Обновление страницы при живом вопросе | Вопрос виден один раз и принимает один ответ. |
| Backend перезапущен, handle устарел | Кнопка ответа недоступна; история вопроса сохранена. |
| Разрыв SSE | После переподключения статус и значимые события не потеряны. |

## Критерии приёмки

- [ ] UI после обновления показывает состояние из БД и продолжает поток событий.
- [ ] Ответ направляется только живому запросу текущей generation.
- [ ] Устаревшие и неопределённые вопросы имеют понятный статус и дальнейшее действие.

## Ожидаемые артефакты

Правила восстановления pending requests и интеграционные сценарии UI/API.

## Открытые вопросы

Может ли целевой App Server сохранять pending server request после потери соединения? До фактической проверки не считать это поддерживаемым.
