# 04.04. Продолжение и потеря thread

> Статус: план реализации; реальный resume проверяется на целевой версии Codex в 02.10 и здесь.

## Цель

Безопасно использовать сохранённый thread после перезапуска и явно обрабатывать невозможность продолжения.

## Зависимости и границы

**Зависимости:** 04.01–04.03, 02.06/02.10, 03.02. Входит: вызов resume, классификация результата и подготовка безопасного нового контекста. Не входит: автоматическое возобновление неизвестного активного turn или повтор потенциально опасной операции после сбоя; это 11.

## Последовательность реализации

1. После старта backend прочитать сохранённые session/runtimeThreadId и подтвердить совместимость версии runtime.
2. Запросить resume через adapter и различить подтверждённый thread, отсутствующий thread, несовместимый профиль и сбой связи.
3. При подтверждённом resume разрешить новый execution только после сверки статуса предыдущего; неизвестный исход передать на процедуру 11.
4. При невозможном resume сохранить причину и подготовить вариант новой session с явным контекстом 04.03 для решения вызывающего модуля или пользователя.
5. Проверить историю до/после рестарта на fake runtime и реальной поддерживаемой конфигурации.

## Тестовые сценарии

| Сценарий | Ожидаемый результат |
|---|---|
| Thread существует и resume подтверждён | Связь восстановлена; новый turn может быть запущен после безопасной сверки. |
| Thread отсутствует | Старая session помечена непригодной, причина сохранена. |
| Старый execution имеет неизвестный исход | Новый turn не запускается автоматически. |

## Критерии приёмки

- [ ] Resume подтверждён ответом runtime, а не наличием ID в SQLite.
- [ ] Потеря thread не выдаётся за восстановленную session.
- [ ] Новый контекст доступен для ручного безопасного повтора без скрытого повторения действий.
- [ ] Реальное поведение целевой версии проверено отдельно от fake сценариев.

## Ожидаемые артефакты

Политика resume, классификация причин отказа, тесты и отчёт совместимости.

## Открытые вопросы и проверки

Какие сведения о завершённом turn доступны после рестарта, выясняется в 02.10. До этого нельзя обещать автоматическое восстановление активного execution.
