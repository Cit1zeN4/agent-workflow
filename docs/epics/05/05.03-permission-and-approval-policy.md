# 05.03. Политика разрешений и утверждений

## Цель

Определить, когда действие требует ответа пользователя и какие решения допустимы.

## Зависимости и границы

Зависит от 05.01–05.02 и ограничений безопасности проекта. HITL принимает и проверяет решение; 06 определяет бизнес-точку утверждения плана, 07 ограничивает пути, 09 владеет push/merge.

## Последовательность реализации

1. Составить матрицу операций: автоматическое выполнение, запрос разрешения, безусловный отказ, запрос вмешательства. Привязать каждую строку к конкретному действию и области действия.
2. Для разрешения определить текст действия, целевой проект/workspace, срок ответа, допустимые варианты и правило повторного использования. По умолчанию разрешение относится к одному запросу.
3. Развести разрешение runtime-действия и утверждение бизнес-артефакта: ответ на один запрос не заменяет другое согласие.
4. При отказе и истечении срока зафиксировать исход и остановить зависимое действие. Не формировать ответ «разрешить» без явного решения пользователя.
5. Описать диагностический маршрут для невозможного, устаревшего или конфликтующего запроса.

## Тестовые сценарии

| Сценарий | Ожидаемый результат |
|---|---|
| Нет ответа на требуемое разрешение | Действие не продолжается. |
| Утверждён план | Разрешение на отдельную Git-операцию не возникает автоматически. |
| Отказ пользователя | Отказ сохранён и передан только связанному запросу. |

## Критерии приёмки

- [ ] Каждая поддерживаемая операция имеет явное правило.
- [ ] Утверждение плана не расширяет область runtime-разрешений.
- [ ] Отказ, истечение и недоступный runtime имеют определённый результат.
- [ ] Матрица не обещает защиту команд одним Git worktree.

## Ожидаемые артефакты

Матрица политики и контракт решения пользователя.

## Открытые вопросы

Какие действия runtime реально выделяет в отдельные approval requests? Уточнить по 05.01.
