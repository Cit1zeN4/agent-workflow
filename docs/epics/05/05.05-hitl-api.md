# 05.05. API ожидающих запросов

## Цель

Предоставить Web UI точный список ожидающих решений и контракт отправки ответа.

## Зависимости и границы

Зависит от 05.02–05.04 и локального API этапа 01. UI реализуется в 10; SSE и replay принадлежат 03. В этом задании фиксируется контракт API до реализации.

## Последовательность реализации

1. Определить операции чтения pending/history по run и отправки решения по requestId. Согласовать структуру с локальным API и правилами доступа из 01.
2. Для каждого типа предоставить понятные UI поля и допустимые варианты без сырых protocol DTO; исключить секреты и небезопасные диагностические данные.
3. Ввести проверку версии/статуса запроса при ответе и различимые ошибки: неверный ввод, конфликт, истёкший запрос, runtime недоступен.
4. После ответа отдать актуальный статус; события 03 сообщают последующие изменения.
5. Зафиксировать примеры запросов/ответов и проверки контракта для потребителя UI.

## Тестовые сценарии

| Сценарий | Ожидаемый результат |
|---|---|
| Обновление страницы с pending | API возвращает тот же запрос и варианты. |
| Ответ с устаревшей версией | Конфликт без нового действия. |
| Запрос чужого run | Не возвращаются данные или возможность ответить на него. |

## Критерии приёмки

- [ ] Описаны входы, ответы, ошибки и примеры для каждого поддержанного типа.
- [ ] Ответы API не раскрывают runtime handle и секретные данные.
- [ ] Конфликт и недоступность отличаются от успешного ответа.
- [ ] Проверены права и связь request с выбранным run.

## Ожидаемые артефакты

Локальный API-контракт, контрактные проверки и примеры для UI.

## Открытые вопросы

Нужен ли отдельный endpoint истории или достаточно общего read model run? Решить после согласования потребностей 10.
