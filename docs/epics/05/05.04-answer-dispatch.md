# 05.04. Ответ и защита от дублей

## Цель

Доставлять решение ровно одному живому запросу и не повторять действие из-за гонки ответов.

## Зависимости и границы

Зависит от 05.02–05.03 и respondToRuntimeRequest из 02.05. Долговременная сверка после сбоя принадлежит 11.

## Последовательность реализации

1. Проверить версию запроса, pending-статус, допустимый вариант ответа и связь request handle с runtime generation.
2. Атомарно захватить право обработки ответа в хранилище; конкурентному ответу вернуть конфликт с текущим состоянием.
3. Для runtime request передать типизированное решение адаптеру. ACK отправки не считать доказательством выполнения действия; итог отражать отдельно.
4. Для внутреннего утверждения обновить бизнес-решение через владельца этапа без имитации runtime response.
5. При disconnect, timeout или неизвестном исходе пометить необходимость сверки. Не повторять отправку, если нельзя доказать, что прежняя не была принята.

## Тестовые сценарии

| Сценарий | Ожидаемый результат |
|---|---|
| Два одинаковых ответа одновременно | Одно решение принято; второе получает предсказуемый конфликт/уже обработано. |
| Противоречащие ответы | Сохранён первый подтверждённый исход, второй не меняет его. |
| Runtime завершился перед ответом | Старый request handle не используется; состояние требует сверки. |

## Критерии приёмки

- [ ] Конкурентные ответы не создают повторных runtime responses.
- [ ] Проверяются принадлежность запроса и актуальность generation.
- [ ] Неопределённая доставка не трактуется как успех.
- [ ] История отказов и конфликтов доступна для диагностики.

## Ожидаемые артефакты

Сервис обработки ответов, таблица ошибок и тесты гонок.
