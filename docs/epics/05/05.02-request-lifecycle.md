# 05.02. Модель запроса и жизненный цикл

## Цель

Сделать ожидающий запрос наблюдаемым и однозначно связанным с execution.

## Зависимости и границы

Зависит от 03, 04 и 05.01. Этап 02 поставляет opaque request handle; этап 03 обеспечивает атомарное хранение. UI-форма относится к 10, восстановление умершего runtime — к 11.

## Последовательность реализации

1. Определить типизированные варианты: текст, один выбор, несколько вариантов, разрешение, утверждение результата, вмешательство при ошибке. Варианты без подтверждения 05.01 пометить как внутренние или неподдерживаемые.
2. Хранить requestId, runId, executionId, sessionId при наличии, runtime generation/handle, тип, безопасный payload, время открытия, срок действия и статус.
3. Ввести переходы pending → answering → answered/denied/expired/invalidated. У каждого перехода должен быть владелец и основание.
4. Сохранение запроса и события выполнить атомарно. Перевод execution в ожидание согласовать с 06 без обхода его машины состояний.
5. Исключить из журнала секреты и ненужные сырые payload; ссылку на диагностический transcript хранить отдельно.

## Тестовые сценарии

| Сценарий | Ожидаемый результат |
|---|---|
| Два запроса в одном execution | У каждого свой идентификатор и история; ответы не смешиваются. |
| Истечение срока | Запрос перестаёт принимать ответы и оставляет объяснимый статус. |
| Сбой записи | Нет pending без соответствующего события или частичного перехода. |

## Критерии приёмки

- [ ] Статусы и допустимые переходы определены для каждого типа запроса.
- [ ] Связь с execution и runtime generation сохраняется после перезапуска.
- [ ] Событие и состояние фиксируются атомарно.
- [ ] Содержимое журнала ограничено необходимым для восстановления и диагностики.

## Ожидаемые артефакты

Модель HITL request, таблица переходов, операции репозитория и контракт событий.

## Открытые вопросы

Каков допустимый срок ответа для каждого подтверждённого runtime request? Значение определить по поведению целевой версии и политике продукта.
