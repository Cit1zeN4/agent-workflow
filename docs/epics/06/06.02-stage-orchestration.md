# 06.02. Последовательность этапов

## Цель

Запускать фиксированный MVP workflow в разрешённом порядке.

## Зависимости и границы

Зависит от 06.01, 04 и контрактов 02. Последовательность этапов задана docs/project.md; вызов конкретного скилла и подготовка его входа принадлежат 08, выполнение tickets — 09.

## Последовательность реализации

1. Описать этапы grill-with-docs → to-spec → to-tickets → implement → code-review → retro. Setup — настройка проекта 08, не часть каждого run.
2. Для каждого этапа определить входной контекст, владельца запуска, ожидаемый результат и переход после успешной проверки.
3. Оркестратор создаёт stage attempt и просит 04 подготовить session, затем передаёт задание исполнителю. Идентификаторы сохраняются до исполнения.
4. Автозапуск следующего этапа выполнять только после положительного вердикта 06.03 и отсутствия паузы, отмены и открытого HITL.
5. Ошибки запуска и неизвестный исход направлять в определённое состояние 06.01 без слепого повтора.

## Тестовые сценарии

| Сценарий | Ожидаемый результат |
|---|---|
| Все проверки пройдены | Этапы следуют заданному порядку без ручного старта каждого. |
| Ошибка в to-spec | to-tickets не запускается. |
| Открыт HITL | Следующий этап не стартует до решения. |

## Критерии приёмки

- [ ] Порядок MVP зафиксирован и покрыт тестом.
- [ ] Не более одного активного execution на run.
- [ ] Ошибка или неопределённость блокирует следующий этап.
- [ ] Setup не запускается при каждом новом run без причины.

## Ожидаемые артефакты

Таблица этапов, оркестратор запусков и контрактные тесты.

## Открытые вопросы

На каком этапе создавать workspace run? Согласовать с 07 до реализации запуска.
