# 06.04. Утверждение плана

## Цель

Остановить workflow после создания tickets до явного утверждения плана реализации.

## Зависимости и границы

Зависит от 05, 06.01–06.03 и результатов to-tickets из 08. Этап 05 хранит и обрабатывает ответ; этап 06 владеет бизнес-правилом разрешения implement.

## Последовательность реализации

1. После положительной проверки to-tickets сформировать запрос утверждения с версией плана, перечнем tickets и ссылками на артефакты.
2. Пока запрос pending, запретить запуск implement и ticket executor 09.
3. При утверждении проверить, что версия плана и набор tickets не изменились; сохранить решение и открыть переход.
4. При отказе или изменении плана оставить gate закрытым и определить допустимое действие: доработка, повтор этапа или отмена run.
5. Не считать runtime permission или успешный turn утверждением плана.

## Тестовые сценарии

| Сценарий | Ожидаемый результат |
|---|---|
| Tickets созданы, ответа нет | Ни один ticket не стартует. |
| План изменён после показа | Старое утверждение отклоняется или требует нового согласия. |
| Отказ | Gate закрыт, решение видно в истории. |

## Критерии приёмки

- [ ] Implement невозможен без решения по актуальной версии плана.
- [ ] Отказ и конфликт не допускают обхода gate.
- [ ] Решение связано с конкретным run и артефактами.
- [ ] История утверждений доступна после рестарта.

## Ожидаемые артефакты

Контракт gate, snapshot плана и тесты принятия/отказа.

## Открытые вопросы

Какие изменения tickets требуют нового утверждения? Определить после формата tracker в 08.
