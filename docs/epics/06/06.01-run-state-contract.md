# 06.01. Состояния и команды run

## Цель

Определить явную машину состояний workflow run, stage и попытки исполнения.

## Зависимости и границы

Зависит от моделей 01, транзакций 03, событий 02 и управления сессией 04. Входит бизнес-контракт состояний; реализация отдельных скиллов относится к 08.

## Последовательность реализации

1. Разделить run, stage, stage attempt и agent execution; не отождествлять terminal turn с успешным stage.
2. Задать состояния run: создан, выполняется, ожидает решения, приостановлен, завершён, отменён, требует вмешательства. Уточнить terminal-статусы и допустимые команды.
3. Задать состояния stage attempt и причины переходов: старт, runtime completion/failure, проверка артефактов, отказ, отмена, неизвестный исход.
4. Описать таблицу допустимых переходов с предусловиями, владельцем команды и обязательным событием.
5. Определить версию состояния для защиты от конфликтующих команд и правило одного активного stage в MVP.

## Тестовые сценарии

| Сценарий | Ожидаемый результат |
|---|---|
| Неизвестный исход turn | Run не становится успешным; требуется отдельная сверка/решение. |
| Два одновременных старта | Создаётся не более одной активной попытки. |
| Недопустимый переход | Явный отказ без изменения состояния. |

## Критерии приёмки

- [ ] Есть таблица переходов и terminal-состояний run/stage/attempt.
- [ ] Все переходы имеют событие и сохраняются через 03.
- [ ] Конкурентные команды не обходят предусловия.
- [ ] Статус runtime не подменяет статус бизнес-этапа.

## Ожидаемые артефакты

Контракт команд, таблица состояний, типы причин переходов и тесты модели.

## Открытые вопросы

Нужно ли отдельное состояние ожидания каждого вида HITL или достаточно общего состояния и активных запросов 05? Уточнить по требованиям UI.
