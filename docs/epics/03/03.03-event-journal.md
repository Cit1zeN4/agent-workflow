# 03.03. Журнал и нормализация событий

> Статус: план реализации; события runtime в реальной базе не проверены.

## Цель

Сохранить упорядоченную историю наблюдений и переходов, пригодную для истории run и доставки UI.

## Зависимости и границы

**Зависимости:** 03.01–03.02, контракт 02.05. Входит: постоянный ID события, версия envelope, тип, связи и безопасный payload. Не входит: wire-парсинг Codex, бизнес-решения по событиям и восстановление неизвестного результата.

## Последовательность реализации

1. Различить события runtime и доменные переходы; сохранять тип, наблюдаемое время, источник и доступные связи с run/session/execution.
2. Назначать постоянный монотонный курсор в момент записи. Runtime generation и sequence сохранять как атрибуты источника, не считать их глобальным курсором.
3. Нормализовать payload до объявленной версии и ограничить объём; чувствительные поля журналировать только при обоснованной необходимости.
4. Определить обработку неизвестного типа, повторной доставки и gaps: отсутствие молчаливого пропуска значимого события.
5. Предоставить чтение по run, execution и курсору в стабильном порядке.

## Тестовые сценарии

| Сценарий | Ожидаемый результат |
|---|---|
| Два runtime generations | Постоянный курсор сохраняет порядок записи. |
| Повтор одного входящего события | Политика дублей даёт предсказуемый результат. |
| Некорректный или слишком большой payload | Ошибка видима, журнал остаётся читаемым. |

## Критерии приёмки

- [ ] У событий есть устойчивый порядок и явные связи с сущностями.
- [ ] Событие состояния фиксируется в той же транзакции, что состояние.
- [ ] Дубли и неизвестные payload не нарушают историю без диагностики.

## Ожидаемые артефакты

Event envelope, таблица типов и операции записи/чтения журнала.

## Открытые вопросы и проверки

Политика хранения объёмных delta-событий и срок хранения определяются по реальным нагрузкам; ключевые переходы нельзя удалять так, чтобы потерять возможность восстановления.
