# AI Development Workflow Orchestrator

**Project Overview & Requirements**

Версия: 1.0  
Статус: Draft  
Целевая платформа: Windows  
AI Runtime: OpenAI Codex CLI  
Режим работы: Semi-Automated / Human-in-the-Loop

---

## 1. Описание проекта

**AI Development Workflow Orchestrator** — локальное приложение с веб-интерфейсом, предназначенное для полуавтоматического управления процессом разработки программного обеспечения с использованием AI-агентов.

Приложение выступает в роли оркестратора, который координирует выполнение последовательных этапов разработки: от уточнения требований и подготовки спецификации до реализации, проверки кода и анализа результатов.

В качестве методологической основы используется workflow, построенный на скиллах Matt Pocock (AI Hero Skills).

Для выполнения задач приложение использует локально установленный OpenAI Codex CLI, а для управления процессом предоставляет пользователю единый веб-интерфейс.

Ключевая особенность приложения — поддержка **Human-in-the-Loop (HITL)**: AI-агент самостоятельно выполняет доступные ему операции, но при необходимости запрашивает информацию, разрешения или подтверждения у пользователя.

Таким образом, приложение объединяет автономность AI-агента с контролем разработчика над процессом создания программного обеспечения.

## 2. Проблема, которую решает проект

Современные AI coding agents способны выполнять значительную часть задач по разработке ПО. Однако использование их в рамках структурированного процесса требует постоянного ручного управления.

Разработчик вынужден самостоятельно:

- Запускать необходимые скиллы в правильной последовательности.
- Отслеживать текущий этап разработки.
- Контролировать переходы между этапами.
- Передавать контекст и результаты предыдущих операций.
- Отвечать на вопросы агента через терминал.
- Следить за выполнением задач и зависимостями между ними.
- Контролировать изменения файлов и Git.
- Проверять результаты выполнения.
- Восстанавливать работу после ошибок и прерываний.

Эти действия создают дополнительную когнитивную нагрузку и отвлекают разработчика от архитектурных и продуктовых решений.

**Основная проблема:** отсутствие единого механизма управления многоэтапным AI-assisted development workflow, который сочетает автоматизацию выполнения с контролируемым участием человека.

## 3. Цель проекта

Создать приложение, позволяющее разработчику запускать, контролировать и завершать полный цикл разработки программного обеспечения с минимальным количеством ручных операционных действий.

Система должна автоматически координировать работу AI-агента, управлять его сессиями, сохранять состояние процесса и привлекать пользователя только в предусмотренных ситуациях.

При этом пользователь сохраняет контроль над ключевыми решениями и потенциально опасными действиями.

### 3.1. Основные задачи приложения

**Оркестрация workflow**

Обеспечить последовательное выполнение этапов разработки с автоматическими переходами и проверкой условий завершения.

**Управление AI-агентом**

Предоставить программный механизм запуска Codex, управления сессиями, обработки событий и получения результатов.

**Human-in-the-Loop**

Обеспечить возможность интерактивного взаимодействия пользователя с AI-агентом без необходимости переключаться в терминал.

**Управление контекстом**

Сохранять и передавать необходимый контекст между этапами разработки, включая документацию, решения, спецификации и результаты выполнения задач.

**Управление задачами**

Обеспечить выполнение implementation tickets с учётом зависимостей и отслеживанием результатов.

**Контроль изменений**

Предоставить механизмы работы с Git, изоляции рабочих пространств и просмотра изменений.

**Наблюдаемость**

Предоставить пользователю информацию о текущем состоянии workflow, действиях агента, ожидающих запросах и результатах.

**Устойчивость**

Обеспечить сохранение состояния и безопасное восстановление выполнения после ошибок и перезапусков.

## 4. Целевая аудитория

Основная целевая аудитория — индивидуальные разработчики, использующие AI coding agents для реализации программных проектов.

Типичный пользователь:

- Работает с локальными Git-репозиториями.
- Использует Codex CLI для разработки.
- Хочет следовать структурированному процессу разработки.
- Предпочитает делегировать AI рутинные операции.
- Хочет сохранять контроль над требованиями, архитектурой и результатами.

В рамках MVP приложение ориентировано на одного локального пользователя.

## 5. Основной сценарий использования

1. Пользователь открывает приложение в браузере.
2. Подключает существующий Git-репозиторий.
3. Выполняет первоначальную настройку Matt Pocock Skills.
4. Отвечает на вопросы конфигурации через Web UI.
5. Создаёт новый workflow run и описывает задачу разработки.
6. Приложение запускает `/grill-with-docs`.
7. AI-агент уточняет требования, задавая вопросы пользователю.
8. После завершения уточнения требований система переходит к подготовке спецификации.
9. На основе спецификации создаётся набор implementation tickets.
10. Пользователь утверждает план реализации.
11. Приложение последовательно выполняет tickets с помощью Codex.
12. Система проводит необходимые проверки и code review.
13. Выполняется retrospective.
14. Пользователь получает результаты разработки, историю выполнения и итоговое состояние Git-репозитория.

При возникновении вопросов, ошибок или необходимости подтверждения workflow приостанавливается и ожидает действий пользователя.

## 6. Поддерживаемый workflow

В качестве основы используется следующий процесс:

| Этап | Skill | Назначение |
|---|---|---|
| 0 | `/setup-matt-pocock-skills` | Первоначальная настройка проекта |
| 1 | `/grill-with-docs` | Уточнение требований |
| 2 | `/to-spec` | Формирование спецификации |
| 3 | `/to-tickets` | Декомпозиция на задачи |
| 4 | `/implement` | Реализация задач |
| 5 | `/code-review` | Проверка изменений |
| 6 | `/retro` | Анализ результатов |

Setup выполняется при первоначальной настройке проекта и при необходимости повторной конфигурации.

Остальные этапы относятся к отдельному workflow run.

Система должна поддерживать особенности скиллов, включая интерактивные вопросы, работу с документацией, создание артефактов и требования к сохранению или обновлению контекста.

Конкретные правила вызова скиллов, проверки результатов и управления сессиями определяются интеграционным модулем.

## 7. Режим автоматизации

Приложение использует **полуавтоматический режим выполнения**.

В этом режиме:

- Следующий этап запускается автоматически после успешного завершения предыдущего и выполнения необходимых условий.
- Пользователь не обязан вручную запускать каждый скилл.
- AI-агент может выполнять разрешённые операции без дополнительных подтверждений.
- При необходимости получения информации выполнение приостанавливается.
- Потенциально опасные действия требуют разрешения.
- На заранее определённых контрольных точках требуется утверждение результата.
- Пользователь может вручную приостановить или отменить выполнение.

Автоматизация не должна обходить установленные ограничения безопасности и политики разрешений.

## 8. Функциональные требования

### FR-01. Управление проектами

Система должна позволять:

- Подключать локальные Git-репозитории.
- Проверять корректность пути и состояние репозитория.
- Хранить конфигурацию каждого проекта.
- Отображать список подключённых проектов.
- Создавать изолированные рабочие пространства для выполнения задач.

### FR-02. Управление workflow

Система должна позволять:

- Создавать workflow run для выбранного проекта.
- Запускать выполнение.
- Отслеживать текущий этап.
- Автоматически переходить между этапами.
- Приостанавливать и продолжать выполнение.
- Отменять workflow.
- Повторно запускать неуспешные этапы.
- Просматривать историю запусков.

### FR-03. Интеграция с Codex

Система должна:

- Запускать локальный Codex App Server.
- Использовать JSON-RPC для взаимодействия с runtime.
- Создавать и продолжать Codex threads.
- Запускать turns.
- Получать структурированные события выполнения.
- Обрабатывать ошибки и завершение процессов.
- Поддерживать прерывание выполнения.

### FR-04. Human-in-the-Loop

Система должна поддерживать:

- Вопросы с текстовым ответом.
- Вопросы с выбором одного или нескольких вариантов.
- Запросы разрешений на действия.
- Запросы утверждения результатов.
- Запросы вмешательства при ошибках.
- Сохранение пользовательских ответов.
- Продолжение выполнения после обработки ответа.
- Защиту от повторной и конфликтующей отправки ответов.

### FR-05. Управление сессиями

Система должна:

- Различать workflow run, agent session и agent execution.
- Создавать новые сессии.
- Продолжать существующие сессии при поддержке runtime.
- Использовать общую сессию для связанных этапов.
- Создавать независимые сессии для отдельных tickets.
- Сохранять идентификаторы и метаданные сессий.
- Обрабатывать потерю и невозможность восстановления сессии.

### FR-06. Интеграция скиллов

Система должна:

- Поддерживать установку и настройку Matt Pocock Skills.
- Запускать необходимые скиллы.
- Передавать им контекст проекта.
- Обрабатывать интерактивные запросы.
- Определять завершение выполнения.
- Проверять наличие ожидаемых артефактов.
- Передавать результаты следующим этапам.

### FR-07. Управление tickets

Система должна:

- Получать задачи из поддерживаемого локального tracker.
- Отображать задачи и зависимости.
- Определять порядок выполнения.
- Запускать реализацию отдельных tickets.
- Отслеживать состояние задач.
- Фиксировать результаты выполнения.
- Не запускать задачу до завершения обязательных зависимостей.

### FR-08. Работа с Git

Система должна:

- Работать с локальными Git-репозиториями.
- Создавать Git worktrees.
- Использовать отдельные рабочие ветки.
- Отслеживать изменения файлов.
- Предоставлять просмотр Git diff.
- Сохранять информацию о commits.
- Защищать основную ветку от непреднамеренных изменений.

### FR-09. Артефакты разработки

Система должна предоставлять доступ к результатам выполнения workflow, включая:

- Документацию проекта.
- Спецификации.
- Архитектурные решения.
- Implementation tickets.
- Результаты тестирования.
- Результаты code review.
- Retrospective.
- Git changes.

### FR-10. Мониторинг выполнения

Система должна отображать:

- Текущий workflow и его состояние.
- Активный этап.
- Выполняемые действия агента.
- Сообщения и события runtime.
- Ожидающие запросы HITL.
- Ошибки выполнения.
- Результаты завершённых этапов.

### FR-11. Сохранение и восстановление

Система должна:

- Сохранять состояние workflow в постоянном хранилище.
- Вести журнал событий.
- Восстанавливать состояние интерфейса после переподключения.
- Определять незавершённые executions после перезапуска backend.
- Использовать доступные механизмы продолжения Codex threads.
- Предоставлять безопасный способ ручного восстановления.
- Не повторять автоматически потенциально опасные действия с неизвестным результатом.

## 9. Нефункциональные требования

### NFR-01. Локальное выполнение

Backend и Codex CLI должны выполняться на компьютере пользователя.

Приложение не должно требовать собственной облачной инфраструктуры для работы.

При этом AI-запросы Codex могут обращаться к внешним сервисам в соответствии с механизмами используемого runtime.

### NFR-02. Совместимость

Целевая платформа MVP — Windows.

Исходная проверенная конфигурация:

- Codex CLI 0.163.0.
- Node.js 24.21.0.
- Git for Windows 2.55.0.

Поддерживаемые версии и совместимость должны быть проверены автоматизированными тестами.

### NFR-03. Безопасность

Система должна:

- Ограничивать доступ к локальному API.
- Проверять пользовательские разрешения.
- Контролировать доступ к файловой системе.
- Исключать небезопасную интерполяцию команд.
- Не предоставлять браузеру прямой доступ к выполнению системных команд.
- Изолировать изменения через рабочие пространства.
- Не выполнять автоматический push или merge без подтверждения.

Git worktree не рассматривается как полноценный security sandbox.

### NFR-04. Надёжность

Система должна обеспечивать согласованность состояния workflow, корректную обработку ошибок и защиту от дублирования операций.

### NFR-05. Расширяемость

Архитектура должна позволять в дальнейшем добавлять другие AI runtimes через адаптеры, не изменяя основную логику Workflow Engine.

### NFR-06. Наблюдаемость

Ключевые действия приложения должны сопровождаться структурированными событиями и диагностическими журналами.

### NFR-07. Удобство использования

Пользователь должен иметь возможность пройти основной workflow через Web UI без ручного запуска команд Codex в терминале после первоначальной установки окружения.

### NFR-08. Сопровождаемость

Приложение должно иметь модульную структуру, типизированные контракты, автоматизированные тесты и документацию ключевых архитектурных решений.

## 10. Архитектурные ограничения

Для MVP принимаются следующие решения:

| Область | Решение |
|---|---|
| Frontend | React + TypeScript |
| Backend | Node.js + TypeScript |
| AI Runtime | Codex CLI |
| Runtime Protocol | App Server / JSON-RPC / stdio |
| Workflow Orchestration | State Machine |
| Persistent Storage | SQLite |
| Real-time Events | SSE |
| Version Control | Git |
| Workspace Isolation | Git worktree |
| Deployment | Local Windows Application with Web UI |

Архитектура должна разделять ответственность между Workflow Engine, Session Manager, HITL Manager, Agent Runtime Adapter, Project Manager и Persistence Layer.

## 11. Границы MVP

В MVP входят:

- Один локальный пользователь.
- Локальные Git-репозитории.
- Один AI runtime — Codex.
- Последовательное выполнение workflow.
- Интеграция Matt Pocock Skills.
- Human-in-the-Loop.
- Управление сессиями.
- Локальный tracker задач.
- Web UI.
- Сохранение и восстановление состояния.
- Базовые Git-операции и code review.

В MVP не входят:

- Облачный backend.
- Многопользовательская работа.
- Параллельные AI-агенты.
- Поддержка Claude Code и других runtimes.
- Jira и Linear.
- Удалённые execution workers.
- Автоматический deployment.
- Автоматический merge в основную ветку.

## 12. Критерии успешности MVP

MVP считается готовым, если пользователь может выполнить полный цикл разработки на тестовом Git-репозитории через Web UI.

Обязательные критерии:

1. Подключён существующий Git-репозиторий.
2. Выполнена первоначальная настройка скиллов.
3. Создан workflow run.
4. Пройден интерактивный этап уточнения требований.
5. Создана спецификация.
6. Созданы implementation tickets с зависимостями.
7. Пользователь утвердил план реализации.
8. Выполнены минимум два зависимых tickets.
9. Изменения зафиксированы в Git.
10. Выполнены проверки кода.
11. Выполнен retrospective.
12. Пользователь может просмотреть результаты и историю workflow.
13. Проверено восстановление после перезапуска интерфейса.
14. Проверено безопасное поведение после прерывания backend или агента.
15. Подтверждена работа HITL с фактически используемой версией Codex.

## 14. Ключевые риски и открытые вопросы

**Совместимость интерактивных скиллов с Codex App Server.**

Необходимо подтвердить, что используемые скиллы могут передавать вопросы через структурированные механизмы runtime.

**Восстановление ожидающих HITL-запросов.**

После потери процесса не всегда возможно продолжить исходный интерактивный запрос. Требуется безопасный механизм восстановления.

**Изменения протокола Codex.**

App Server является экспериментальным интерфейсом. Необходимо фиксировать поддерживаемые версии и проверять совместимость.

**Определение завершения скиллов.**

Успешное завершение turn не всегда означает успешное завершение бизнес-этапа. Требуются отдельные проверки результатов.

**Совместимость локального tracker.**

Необходимо определить и проверить формат задач, поддерживаемый выбранными скиллами.

**Безопасность локального исполнения.**

Работа AI-агента с терминалом и файловой системой требует ограничений, журналирования и явных политик разрешений.

## 15. Видение дальнейшего развития

После завершения MVP архитектура может быть расширена для поддержки дополнительных AI coding agents, настраиваемых workflow, интеграций с внешними issue trackers, нескольких одновременно выполняемых проектов и распределённых execution environments.

Однако эти возможности не должны усложнять реализацию первоначальной версии.

---

## 16. Итоговое определение продукта

**AI Development Workflow Orchestrator — это локальная система управления AI-assisted software development, которая превращает последовательность отдельных AI-скиллов в единый, контролируемый, наблюдаемый и восстанавливаемый процесс разработки программного обеспечения.**

Приложение берёт на себя операционное управление workflow, позволяя разработчику сосредоточиться на постановке задач, принятии решений и оценке результатов.
